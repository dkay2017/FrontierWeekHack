TireForge Anomaly-Fault IQ — Build Logic Plan

Baby-steps sequence for the functional build. Pure functions first, AI stubbed, Adapter-only-write from the start. Every step has a check in italics.

  • Project: TireForge Anomaly-Fault IQ — MS Agent-a-Thon, Architect Track, Factory scenario
  • Author: Deepak Kumar  ·  Date: 2026-09-01
  • Source of truth: TireForge-Anomaly-Fault-IQ-TDD.docx, Tireforge-Architecture_design.html/.svg
  • Working dir: Implementation/ (greenfield)

1. Invariants (hold for every step)

  1. Work Order Adapter is the only write path.
  2. Every agent verdict cites its source record (rdg-… / inc-…).
  3. confidence < 0.70 OR severity == "crit" → human review. Exactly 0.70 → auto.
  4. Agents may only read + write WorkOrders. Nothing touches equipment.
  5. Cost figures come from real APIM token metrics, never mocked.
  6. Health Report is a dashboard tab, not an agent.

Flow: Emit → Buffer → Trigger → Check → Detect → Match → Diagnose → Gate → Act → Review → Report

2. Stage A — Data model

  1. Schema DDL: Machines, Readings (+is_anomaly), History, Diagnoses, WorkOrders. (5 tables create)
  2. Seed 5 machines + bands t/p/v/r [lo,hi] + units. (query returns 5)
  3. Seed History with ~8 past incidents. (rows present)
  4. Data-access module: get_machine, insert_reading, etc. (round-trip tests pass)

3. Stage B — Make a reading

  1. make_reading(machine, mode) — modes normal / warn / crit. (normal in-band, crit out)
  2. reading_id() → rdg-<ts>-<rand>. (unique, sortable)
  3. Persist reading with is_anomaly = NULL. (row present)

4. Stage C — ThresholdCheck (T1), pure

  1. threshold_check(reading, machine) → per-sensor {value, band, status: ok/low/high, deviation%}. (table tests)
  2. Seed severity from worst deviation → info / warn / crit. (boundary tests)
  3. "T1" trace line cites rdg-id + offending sensor. (id in string)

5. Stage D — Anomaly Detection (A1), stubbed

  1. Interface: detect_anomaly(reading, t1, recent) → {is_anomaly, text, cites}.
  2. Stub: is_anomaly = any sensor out of band; text cites rdg-id. (tests)
  3. Write is_anomaly back onto the reading. (column updated)
  4. Early exit: not anomaly → stop. (no Diagnoses/WO rows)

6. Stage E — HistoryMatch (T2), pure

  1. Fault signature from T1 (e.g. vib-high+temp-high). (tests)
  2. history_match(machine, signature) → {incidents, text, cites:[inc-…]}. (matches seed data)
  3. "T2" trace line cites inc-id. (id in string)

7. Stage F — Fault Diagnosis (A2), stubbed

  1. Interface + structured output: {fault, severity, confidence 0–1, text, cites:[rdg,inc]}. (schema validates)
  2. Stub: deviation + history → fault/severity/confidence; tune so some <0.70, some crit. (spread across inputs)
  3. Persist Diagnoses row with full trace (detect/match/diagnose text). (row present)

8. Stage G — The Gate

  1. gate(dx) → {route: auto/review, reason} per rule 1.3. (truth table)
  2. Record gate reason on the Diagnoses row. (field set)

9. Stage H — Work Order draft (A3), stubbed

  1. Interface: draft_work_order(dx) → {machine, fault, severity, reading_id, action_text}.
  2. Stub: template from diagnosis; cites reading. (fields populated)

10. Stage I — Act (only write path)

  1. Adapter write_work_order(payload, by) → WO-id, status = issued. Sole writer. (WO row)
  2. auto route → Adapter directly; Diagnoses.status = auto-issued. (WO + link)
  3. review route → Diagnoses.status = pending, no WO. (zero WO rows)

11. Stage J — Compose

  1. run_pipeline(reading) = C→D→E→F→G→H→I, one trace_id. (normal stops at D · warn → auto WO · crit → pending)
  2. One structured log line per step (trace_id + citation). (one trace shows all steps)

12. Stage K — Reviewer decisions

  1. approve(dx-id, reviewer) → Adapter writes WO by=reviewer; status = approved. (WO row)
  2. reject(dx-id, reviewer, note) → Adapter writes audit row status = rejected; no active WO. (audit row)
  3. close(WO-id) → closed, only from issued / approved. (bad transitions rejected)

13. Stage L — Report logic (pure reads)

  1. /status → machines + bands + latest reading. (matches contract)
  2. /queue → pending Diagnoses + full trace. (matches contract)
  3. /workorders → list + lifecycle. (matches contract)
  4. Health metrics → anomalies-by-machine-24h, resolution rate, open/closed. (reconcile with store)
  5. /cost → sum stored token/cost fields (real APIM at Phase 4). (matches contract)

14. Stage M — Swap stubs for real agents (one at a time)

  1. A1 real (gpt-4.1-mini) → diff vs stub on the 4 eval scenarios. (agree on clear cases)
  2. A2 real (gpt-4.1) → verify structured output + confidence sanity. (schema valid, gate behaves)
  3. A3 real (gpt-4.1-mini). (WO fields well-formed)

15. Notes

  1. Stages A–L need no cloud and no model — all local, all testable.
  2. Queue / Durable Functions wiring wraps around run_pipeline later without changing logic.
  3. Schema additions from the dashboard-feasibility review: is_anomaly on Readings, Diagnoses table for the pending trace, reject = WorkOrders audit row.
